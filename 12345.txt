# Development Plan — Taskbar Banner App for Windows 10 / Windows 11

## 1. Overview
A Windows desktop app that runs on **Windows 10 and Windows 11**. It displays an
advertiser banner (logo + short text) docked next to the system-tray icons inside the
taskbar, and it records **active seconds** of genuinely "watched" time. Recording only
starts after an initial **five-minute warm-up** period of continuous user activity, stops
when the user is **inactive for 60 seconds** (or the system becomes locked/suspended/the
taskbar is auto-hidden), saves the accumulated seconds to the **user's record**, and only
resumes after a **fresh five-minute warm-up**. Clicking a banner raises the app window;
from the app the user can open the advertised website.

This revision supersedes the previous plan and encodes the product refinements listed in
§2.

## 2. Refinement Summary (changes vs. previous plan)
1. **OS targets made explicit:** the app must run on **Windows 10 and Windows 11**
   (see §3 and §13).
2. **Recording unit changed from "verified minutes" to seconds.** Accumulated time is
   recorded/saved in **seconds**, after a **five-minute warm-up** (see §7).
3. **Explicit idle rule:** if the user is **inactive for 60 s**, the counter stops, the
   accumulated time is **saved to the user's record**, and counting resumes only after a
   new **five-minute warm-up** (§7).
4. **Active-action catalog and idle definition** are now explicit (§6).
5. **Banner geometry:** the banner height must equal the **taskbar height** (§9).
6. **Taskbar auto-hide gating:** on startup the app must check whether taskbar auto-hide
   ("hiding") is enabled; if so it shows a notification that the setting must be disabled,
   and the counter **must not operate** while auto-hide is enabled (§8).
7. **Demo/visual-verification deliverable:** a **portable .exe** must be built and a
   **temporary registration placeholder** (simulating a registered user) must be
   implemented so the app can be demonstrated without a real server or real OAuth (§10,
   §16).
8. **Portability:** the delivered file must be **transferable to another computer**
   (self-contained, no runtime install) (§4).

## 3. Supported OS & Runtime Targets
- **Windows 10** (all supported feature releases) and **Windows 11** (incl. 23H2/24H2-era).
- Target framework `net8.0-windows` (or newer LTS available at build time), any-CPU pinned
  to `win-x64` for the deliverable exe.
- Must not rely on OS-version-specific APIs without a fallback; the two places where
  Windows 10 and Windows 11 differ materially — taskbar metrics / auto-hide detection and
  the taskbar settings path — are handled explicitly (§8, §13).
- UI scaling / DPI awareness: **per-monitor v2 DPI aware**; banner and taskbar metrics are
  computed in physical pixels from the taskbar rect.

## 4. Tech Stack & Packaging (portable deliverable)
- **Language/Platform:** C# (.NET 8), **WPF** (main app + borderless overlay banner).
- **Packaging (requirement "transferable to another computer"):** publish a
  **self-contained, single-file win-x64 .exe**
  (`dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true
  -p:IncludeNativeLibrariesForSelfExtract=true`). The single file includes the .NET
  runtime, so it runs on a clean Windows 10/11 PC **without installing anything**.
- **Persistence:** SQLite via SQLitePCLRaw "bundle_e_sqlite3" provider so the native
  engine is embedded in the publish output (no external DLL). Local DB is created under
  `%LocalAppData%\TaskbarBannerApp\` on first run.
- **WebView2:** NOT required for the demo build. It is reserved for the later real OAuth
  flow (§12) and would be an opt-in runtime dependency then. Keeping it out of the demo
  build maximizes portability.
- **No backend needed for demo:** the demo uses a simulated registered user (§10) and
  stores everything locally. Real REST/OAuth are deferred (§12).

## 5. System Architecture / Modules
1. **Tray/Banner Overlay Module** — borderless, topmost, non-activating windows
   (`WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST`), never steal focus. One overlay
   per taskbar (incl. **secondary monitors**), positioned immediately to the left of the
   notification-area/tray cluster. **Overlay height = taskbar height** (§9). Clicking an
   overlay raises the main app window (no direct navigation).
2. **Taskbar State Module** — `SHAppBarMessage(ABM_GETTASKBARPOS)` (per monitor),
   `FindWindow("Shell_TrayWnd")` / `"Shell_SecondaryTrayWnd"` enumeration as a fallback for
   multi-monitor on both Windows 10 and 11; computes taskbar rect, work area, visibility,
   and **auto-hide state** (`ABM_GETSTATE` / `ABM_GETAUTOHIDEBAR` per monitor). Re-queries on
   taskbar change / display-change / resolution-change / DPI-change events.
3. **System State Module** — `SystemEvents.SessionSwitch` (lock/unlock),
   `SystemEvents.PowerModeChanged` (suspend/resume), session connect/disconnect.
4. **Activity Module** — `GetLastInputInfo` (ms-resolution) plus a per-second tick that
   records `lastInputUtc`; classifies activity vs. idle (§6). Optional phase-2 heuristic
   signal: foreground media playback (SMTC) to treat unattended video as idle.
5. **Warm-Up / Recording Engine** — 1-second tick; explicit state machine (§7); flushes
   runs to the user's record on stop.
6. **Record Store** — SQLite "user's record" of accumulated active seconds and run history
   (§11).
7. **Registration Placeholder (demo)** — simulated "registered user" so the app can be
   visually verified without a server (§10). Swapped out for real **OAuth 2.0** later (§12).
8. **Ad/Banner Content Module (demo)** — a bundled/offline demo ad (logo + short text);
   real ad rotation from the server is deferred (§12).

## 6. Activity vs. Idle — Definitions and Detection

### 6.1 "Active actions" (what counts as user activity)
The app counts a session as active when the user is demonstrably interacting with the PC.
The following catalog defines what "active" means; it is detected at the OS level, not by
instrumenting individual applications:

| # | Active action | Detection signal |
|---|---------------|------------------|
| 1 | Data entry: keystrokes, typing, keyboard shortcuts | keyboard input events |
| 2 | Mouse/touchpad: clicking, scrolling, dragging, text selection | mouse/pointer input events (incl. wheel) |
| 3 | Window/interface management: open/close/min/max windows, switching tabs/apps | pointer/keyboard input + foreground-window change events |
| 4 | Launching/using programs: apps, editors (Word/Excel), browsers, graphics/video editors, IDEs | input events produced while working in those apps (foreground process recorded in audit log) |
| 5 | Web services: forms, messages, file upload/download, active page use | input events in the browser/app |
| 6 | Files & folders: create/edit/copy/move/delete, archiving | input events (explorer/app); filesystem changes logged in audit trail (optional) |
| 7 | Peripheral devices: scan/print/external drives | interaction happens through apps → input events; device arrival logged (optional) |
| 8 | Communication: video conferences, email, chat, shared docs | input + audio/video-call heuristics (optional phase 2) |
| 9 | Games & interactive applications | input events (keyboard/mouse/gamepad); gamepad support is phase 2 |

**Implementation note:** the authoritative signal is *any* qualifying input event
(keyboard/mouse/pointer). Activity detection never relies on the ability to tell exactly
which catalog item is happening; the catalog is the product definition of the activity the
input signal stands in for. Foreground app/process is recorded alongside counted seconds
for the local audit trail and future server-side plausibility checks.

### 6.2 "Idle time" (what does NOT count)
- The computer is on but there is **no keyboard or mouse input** (primary rule).
- A video or slideshow is playing **without user interaction** (heuristic: foreground media
  playback with no recent input — phase 2 refinement; the 60 s no-input rule already stops
  counting for the pure "watching" case).
- An application runs in the background (updates, sync) while the user does not interact
  with it (automatically idle under the input rule).

**Rule of thumb:** any second that is not part of an active, input-confirmed session is
idle and does not count.

## 7. Counter / Recording Rules (core logic — seconds)

### 7.1 Definitions
- **Qualifying second:** a wall-clock second during which ALL of the following hold:
  - machine is **on** and the session is **unlocked** (not lock screen, not disconnected);
  - **registered** (demo: simulated user created, §10);
  - taskbar auto-hide is **disabled** and the relevant taskbar(s) + banner are visible (§8);
  - at least **one** banner overlay is confirmed rendered/on-screen (self-check each second);
  - the user is **not idle**: `lastInputUtc` is within the trailing **60 s** window (i.e.
    the user has not been inactive for 60 consecutive seconds).
- **Warm-up (priming):** the first **300 qualifying seconds** (5 minutes) of a session
  before any time is recorded. Warm-up seconds are **not** added to the user's record.
- **Counting run:** a continuous stretch of qualifying seconds after warm-up completes.

### 7.2 Rules
1. Recording starts only after **five full minutes of warm-up** (300 qualifying seconds).
2. Every qualifying second after warm-up is accumulated into the current run buffer and
   saved to the **user's record** (flush cadence: at least every 60 s, always on stop).
3. If the user becomes **inactive for 60 consecutive seconds**, the run **stops** and the
   accumulated time is **saved to the user's record** immediately (flush reason `idle_60s`).
4. After any stop — 60 s inactivity, **lock**, **sleep/resume**, **session change**,
   **taskbar auto-hidden**, or **banner not verifiable** — the warm-up resets to 0 and
   counting resumes only after a **new five-minute warm-up**.
5. Short pauses shorter than 60 s inside a warm-up or a run are allowed: they do not reset
   anything, because the user is not yet "inactive for 60 seconds".
6. While taskbar auto-hide is enabled the engine is in a hard **BLOCKED** state: it must
   not operate at all (no warm-up progress, no counting) (§8).
7. Epoch/second boundaries are anchored to wall-clock UTC for future server validation.

### 7.3 State machine
```
UNREGISTERED / taskbar auto-hide ON / locked / sleeping / not visible
        │  (blocked: nothing runs)
        ▼  (registered + unlocked + auto-hide OFF + banner visible)
      WARM_UP ── 300 qualifying seconds ──▶ COUNTING
        ▲                                     │
        │   (interrupt at any second: idle reaches 60 s, │
        │    lock, sleep, taskbar hidden, banner gone)    │
        │                                     ▼
        └────────── save/flush run ── reset warm-up to 0 ─┘
```
Implement as an explicit `enum` state machine with a per-second event log for debugging and
acceptance testing.

## 8. Taskbar Auto-Hide ("Taskbar Hiding") Check & Gating
- **Startup check:** on launch the Taskbar State Module queries every taskbar (primary +
  secondary monitors) for auto-hide. If **any** taskbar where a banner is placed has
  auto-hide enabled → the app shows a **notification** stating that this setting must be
  disabled, e.g. an in-app dialog/tray balloon plus a message on the main window:
  - *Windows 11:* Settings → Personalization → Taskbar → turn **off** "Automatically hide
    the taskbar".
  - *Windows 10:* Settings → Personalization → Taskbar → turn **off** "Automatically hide
    the taskbar in desktop mode".
  - Include an optional "Open settings" button (`ms-settings:taskbar`).
- **Hard gating:** the recording engine **must not operate** while taskbar auto-hide is
  enabled on any relevant taskbar (§7.3 BLOCKED state — no warm-up, no counting).
- **Re-check:** re-evaluate continuously (poll every ~5 s) and on taskbar-state change /
  display events; when the user disables auto-hide, the notification clears and the engine
  may begin its five-minute warm-up.
- Banner overlays are only shown when auto-hide is off (an auto-hidden taskbar leaves no
  guaranteed-visible area for the banner).

## 9. Banner Behavior
- **Size:** banner **height equals the taskbar height** (measured per monitor from the
  taskbar rect). Width is a fixed proportion (e.g. 4:1) or fixed pixel width sized to the
  ad; both computed in physical pixels for the banner's monitor.
- **Position:** sits directly to the left of the notification-area/tray icons on each
  taskbar (including secondary monitors), visually inset inside/on the taskbar band,
  bottom-aligned with the taskbar.
- **Visibility = counting prerequisite:** ≥ 1 overlay confirmed on-screen keeps the session
  qualifying; the overlay self-checks visibility each second.
- **No focus stealing:** overlays use non-activating topmost window styles; clicking one
  focuses the main app window.
- **Self-recovery:** repositions on taskbar move/resize, resolution/DPI changes, and
  monitor add/remove; an overlay for a removed monitor is destroyed, the rest keep working.
- **Demo content:** bundled demo ad (logo + short text); clicking shows the ad details in
  the main app with an "Open website" button.
- Banner overlays appear only for a **registered** (demo-simulated) user with auto-hide
  disabled; unregistered or auto-hidden → no banner, no counting.

## 10. Registration Placeholder (demo / simulated registered user)
Because real OAuth requires a server, the demo build implements a **temporary
registration/session placeholder**:
- The main app shows a simple **"Register (demo)"** screen on first run.
- Clicking it creates a **simulated registered user** locally: a generated `userId`,
  `deviceId`, display name, and session token stored in the local SQLite store.
- After that the app behaves exactly as a fully registered user: banner shown, warm-up and
  counting active (§7), records saved to the user's record (§11).
- Clearly marked as temporary (e.g. "Demo mode — simulated registration"). It is a
  drop-in stand-in for the future OAuth module (§12) and must be replaceable without
  touching the counter/activity/taskbar code.

## 11. Data & "User's Record" (local)
- SQLite DB under `%LocalAppData%\TaskbarBannerApp\tbb.db`.
- Tables (demo scope):
  - `user` — id, display name, `is_demo` = 1, created UTC, device id.
  - `activity_run` — run start UTC, run end UTC, warm-up seconds, **active seconds**
    accrued, stop reason (`idle_60s`, `lock`, `sleep`, `auto_hide`, `banner_hidden`,
    `manual`), user id.
  - `setting` — key/value (e.g. last "auto-hide notification shown" state).
- "Accumulated time saved to the user's record" = sum of active seconds across
  `activity_run` rows for the user (flushed on stop and periodically during a run).
- The delivered portable exe needs no pre-existing data: first run on any PC creates the
  DB, then the demo registration screen (§10) creates the simulated user. Transferring the
  app to another computer = copying the exe; each PC keeps its own local record.

## 12. Deferred Work (out of demo scope, kept in design)
- **OAuth 2.0 (Authorization Code + PKCE)** login/refresh via WebView2; replaces §10
  placeholder; DPAPI token storage; logout clears local session.
- **Server reporting:** batch upload of recorded runs/seconds to `POST /api/v1/minutes`
  with idempotency keys and retry/backoff; replaces local-only storage.
- **Ad rotation** from the API and click → ad → website flow with a real ad catalog.
- Not required for the visual-verification exe; architecture keeps these swappable.

## 13. Windows 10 vs. Windows 11 Specifics
- **Taskbar layout:** Win10 classic left-aligned tray; Win11 centered icons + overflow.
  Overlay is always anchored to the right-end cluster (notification area), so it must read
  the tray cluster bounds rather than assuming icon alignment.
- **Taskbar metrics:** overlay height is always read live from the taskbar rect
  (ABM_GETTASKBARPOS per monitor); never hard-code 40 px (Win10) or 48 px (Win11).
- **Auto-hide state & toggles:** same Win32 API surface on both, but the user-facing
  settings path differs (§8). Notifications must show the correct path per OS version.
- **Multi-monitor:** secondary taskbars exist on both; `Shell_TrayWnd` + `Shell_SecondaryTrayWnd`
  enumeration plus per-monitor `ABM_*` calls cover both OSes. Secondary-monitor edge cases
  (Win10 extended, Win11 multi-display) must be in the manual test matrix.
- **Rounded corners / transparency (Win11):** overlays remain opaque rectangles with
  standard window styles for reliable visibility checks.
- **Verification requirement:** every acceptance test in §15 is run on **both** Windows 10
  and Windows 11.

## 14. Security / Anti-cheat (design note)
- Demo records local data only. Future server-side validation mirrors the client rules
  (seconds must be contiguous within runs; lock/sleep/auto-hide/idle gaps must break runs;
  no implausible totals). Defense-in-depth only — absolute anti-fraud needs future
  server-side heuristics; not in demo scope.

## 15. Testing / Acceptance Criteria
- **Unit tests:** qualifying-second matrix (lock/sleep/auto-hide/idle/not-visible combos),
  warm-up boundary (299 → 300 seconds), idle-60 s stop + flush, re-warm after every
  interrupt, BLOCKED-while-auto-hide logic.
- **Simulated hooks:** injectable system-event sources and a fake input clock; no real
  input required in tests.
- **Manual smoke (Windows 10 and Windows 11):**
  - Start with taskbar auto-hide OFF → banner appears with **height == taskbar height**;
    register (demo) → after 5 min warm-up, seconds accrue.
  - Stop interacting for **60 s** → counter stops and the accumulated seconds appear in the
    user's record; resume → exactly 5 more minutes before seconds accrue again.
  - Start with auto-hide ON → notification is shown and counter does not operate; disable
    auto-hide → notification clears, warm-up begins.
  - Win+L lock, sleep/resume, minimize/restore/move taskbar, resolution/DPI change,
    second monitor attach/detach.
  - Different Windows 10 and Windows 11 machines (incl. one without .NET installed) →
    copy only the exe → runs, registers demo user, records time.
- **Acceptance (demo):** after warm-up + N qualifying seconds on a clean machine, the
  user's record contains exactly the expected run (start/end UTC and N active seconds) and
  survives an app restart.

## 16. Delivery Milestones (order for the agent)
1. **Project scaffold + portable publish:** .NET 8 WPF solution; single-file self-contained
   win-x64 publish script; main window + tray icon; verify the exe runs on a clean Win10
   and Win11 PC.
2. **Registration placeholder (demo):** simulated registered user (§10); after "Register",
   app reaches the registered state locally.
3. **Taskbar state + auto-hide gating:** per-monitor taskbar rect/auto-hide detection
   (§8), startup auto-hide notification with correct OS-specific text, BLOCKED state,
   re-check loop.
4. **Banner overlay:** banner with **height == taskbar height**, positioned next to tray,
   non-activating, self-recovery, visibility self-check.
5. **Activity/idle detection:** per-second input monitoring (GetLastInputInfo), 60 s idle
   rule, activity catalog & idle definition implemented as the engine's input signal (§6).
6. **Warm-up/counting engine + persistence:** 1 s state machine (§7), warm-up/run/flush,
   SQLite user's record (§11), unit tests (§15).
7. **Verification build + hardening:** final portable .exe, manual visual-verification
   script, run acceptance tests on Windows 10 and Windows 11, cleanup demo-mode edge cases.

## Confirmed Decisions (updated)
- **OS support:** Windows 10 and Windows 11 both, verified on each (§3, §13).
- **Recording unit:** seconds, saved after a **five-minute warm-up** (§7).
- **Idle threshold:** user inactive for **60 s** stops the counter and saves the
  accumulated time to the user's record; a **fresh five-minute warm-up** is required before
  counting resumes (§7).
- **Re-priming:** required after every interruption (idle-60 s, lock, sleep, auto-hide,
  banner not visible).
- **Taskbar auto-hide:** startup notification requiring the setting to be disabled; counter
  **must not operate** while enabled; re-checks continuously (§8).
- **Banner height == taskbar height**, docked next to the tray cluster, one overlay per
  taskbar incl. secondary monitors (§9).
- **Demo deliverable:** a **portable self-contained .exe** that is **transferable to
  another computer**, with a **temporary registration placeholder** simulating a registered
  user; real OAuth/server/ad features are deferred but kept swappable (§10, §12, §16).
